# What Micme can learn from Handy

## Finding and evidence boundary

Handy's most useful lesson is to **test the entire take, not just the recognizer**. A recording can lose its first word before inference, a fast model can show stale words while someone speaks, and a correct transcript can paste yesterday’s clipboard. Micme already addresses parts of this chain. Keep direct Pi editor delivery; transfer first-sample readiness, model choice by measured capability, and recovery without re-dictation. System-wide dictation needs a second, optional surface: a terminal extension cannot observe global key releases or insert into another app through Pi’s editor API.

Read the comparison first, then the [phased build requests](roadmap.md#request-for-each-phase). In the inventory below, **keep** means preserve an existing benefit, **adapt** means implement the behavior for Micme rather than copy the UI or change defaults, and **desktop** means a separately installed companion. P numbers identify proposed deliveries, not shipped Micme features. A check describes evidence to collect, not a result.

## How to substantiate parity

1. **Choose the comparison before the run.** Record app/tag/commit, OS/display, CPU/GPU/driver and actual bound device, model revision/quant/hash, language/task, VAD/chunk settings, mic/loopback, output target, prompt contents and cache state. Compare both with the same input and task. Exact same weight/engine where possible; if exports differ, label the result a *product configuration* comparison, not an engine A/B. Keep default install and tuned configuration as separate panels. No compatible model/target → not comparable, not a win.
2. **Use three tracks.** (a) Identical hashed public PCM for ASR-only, WER/CER, byte coverage and compute ×RT. (b) Paced speech through each live capture path on the same host via loopback; actual mic/permission/device trials separate. (c) Observed destination: Handy/companion in a controlled external editor; Pi’s prompt before user sends, never a model response. Different destinations are labelled, not forced into an identical clipboard benchmark. Instrument actual visible text and target state, not solely worker or key events. For unsupported streaming, first draft is *not applicable*, not zero milliseconds.
3. **Measure intervals people notice.** Trigger→first actual samples and ready cue; speech onset→first correct visible pair and sustained relevance/progression; first irreversible commit; release→tail drain→raw final→optional rewrite/hook→complete, correct target contents. Also log failure/no result, missed onset/tail, repeats, stale/duplicate insert, peak lag/RSS, model load, idle mic/resource use. Keep raw ASR, cleaned, displayed, replayed and delivered strings separately on *public fixtures*; production timing logs contain no text.
4. **Score the same speech.** Short/quiet, immediate stop/silence/noise, continuous, pauses/rollover, repeats, numbers/identifiers, non-Latin and multilingual references. Raw WER against a human reference, CER for scripts without suitable word segmentation; explicit translation reviewed for meaning, not source-language WER. Preserve existing [Micme live gates](https://github.com/senad-d/micme/blob/70ad13862563aa46b7bd76411a1df852d9c740b7/test/live-native/README.md#interpreting-the-report): first correct pair median/p95 ≤3/5 s at 80 **and** 40 columns; ≥80% relevant checkpoints, no consecutive misses, progressing tails; ≤20% final WER and ≤10 points worse than matched clip on JFK/continuous. Negative controls must not insert speech. These are Micme regression gates, not Handy numbers.
5. **Publish denominators and limits.** Interleave runs on the same hardware, record cold process/model, warm and idle-reload separately; include contended CPU, optional processing on/off and delivery failures. Separate cache-warm from disk-cold. Predeclare repeats and a tolerance derived from repeated reference runs before looking at candidate results. For timed comparison cells use at least 20 observations/condition, show median/p95, error counts and paired deltas; don't hide timeouts in a fast-success average. Pass a cell only if feature checks pass, delivered reference content/accuracy and success do not regress, and both latency quantiles are no worse than the reference plus the declared noise tolerance. A missing measurement stays **unverified**. No device-independent speed or reliability guarantee follows from passing a cell.

**Bottom line:** a Pi user can benefit from earlier trustworthy feedback, fewer lost takes and more informed model choices without adopting a desktop clipboard workflow. To say “works outside Pi like Handy,” observe the companion completing that workflow. To say “as fast” or “as accurate,” identify the passing comparison cell. The [roadmap](roadmap.md) uses those as distinct release gates.
